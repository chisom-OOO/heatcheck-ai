**How changed code can replay a frozen plan.** The fix edits files inside the frozen `code_hash`
(`custodian.py`, `game_prediction.py`), and RV-R4 changes the file list. So the fixed code can never equal
the plan's `code_hash` (`d496e34e…`).

- `game_prediction.py amend` writes a **CODE_IDENTITY_ONLY** amendment, `evidence/claim_plan_GP.amendment-1.json`
  (hash `94fcd9ce…a24a`). It records only the new code file list and code hash (`656861b1…bfa`) and the plan it
  amends. It carries no claim, hypothesis, threshold, floor, split, data hash, family, epoch or seed.
  `final()` reads all decision content from the original plan.
- With changed code, `final()` runs only if such an amendment matches the current code. It then calls
  `Custodian.replay()`, which requires:
  - the original receipt to be **spent**;
  - the same family, epoch and canonical records;
  - input data equal to any earlier binding.

  A replay exposes no new record. Every replay stays in the ledger and is listed in the result
  (`ledger_history_of_receipt`).
- Without a matching amendment, changed code is refused: "this would be a new experiment".
- Limitation: amendments make repeated code changes visible, but they don't prevent them. Each replay is
  logged, and Max should treat more than one replay of a receipt as a review trigger.
