## 2. Tamper demo

`heatcheck/api/tamper.py`, served by Max's API and forwarded by the page server:
- `POST /api/tamper/flip`, `POST /api/tamper/restore` and `GET /api/tamper/events`.
- One flip per 5 s.
- The committed `evidence/evidence.jsonl` is only read.

**A real run** on the committed file (scratch paths outside the repo):
- File sha256 `14d64245…` before and after.
- Response:
  `{"offset": 24585, "line": 5, "expected": "0x53 'S'", "actual": "0x52 'R'", "verdict": "DATA_INVALID", "error": "ledger line 5: identity hash mismatch (tampered)", "ledger_event_id": "5bd45a04…"}`

**Deviation from the spec:** TAMPER_ATTEMPT events go to their own hash-chained ledger,
`logs/tamper_events.jsonl`, not the dialogue evidence ledger. They are appended with the same class
and the chain stays intact. `heatcheck/agents/loop.py:51` reads `identity["data"]` from every
evidence entry, so a tamper event there would crash the next agent-loop question. The UI's "new
ledger row" can come from `GET /api/tamper/events`.

**Tests** (`tests/integration/test_tamper.py`, 7):
- the real reader rejects the copy;
- exactly one byte differs, inside the verdict value;
- the committed file is byte-identical afterwards;
- the event is a chained entry without the bytes;
- the rate limit;
- restore;
- the HTTP routes, on and off.
